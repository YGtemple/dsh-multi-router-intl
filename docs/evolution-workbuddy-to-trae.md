# 从国际版 WorkBuddy 到 Trae：这段路由逻辑是怎么迁过去的

> 记录这个项目从「改造国际版 WorkBuddy」到「把同一套逻辑接到 Trae」的演进过程。
> 说明为什么后来会变成现在这个多客户端结构。

## 一、起点：只是想改国际版 WorkBuddy

最初的目标很小——国内版 WorkBuddy 能用，国际版（AI international）的对话走不通。想做的只是让国际版也能正常发请求。

当时的工作集中在三件事：

| 环节 | 问题 | 处理 |
|---|---|---|
| 登录态 | 国际版的登录流程与国内版不是同一套 | 单独实现登录，见 `src/workbuddy-login.mjs` |
| 请求路由 | 两边的接口地址与鉴权方式不同 | 按账号区分目标端点 |
| 会话保持 | 国际版对会话续期更敏感 | 在 `src/accounts.mjs` 里做账号级状态管理 |

这一步做完，国际版能用了。但代码是「国内版一套 + 国际版一套」并排摆着，改一处要改两遍。

## 二、转折：发现这其实是一个路由问题

真正让结构变清晰的，是意识到**这跟 WorkBuddy 没关系**。

抛开具体产品，要做的事一直是同一件：

```
给定一个请求 → 判断该由哪个客户端处理 → 转给对应端点 → 把响应接回来
```

WorkBuddy 的国内版和国际版只是这个链条上的两个「客户端」。既然是同一件事，就该只在**客户端描述**上区分，而不是复制整套流程。

于是有了 `src/clients.mjs`——把每个客户端定义成一份描述：

- 端点地址
- 鉴权方式
- 登录流程（哪个要单独实现）
- 能力差异（支持哪些模型、上下文长度）

`src/router.mjs` 只做分发，不认识任何具体产品。

## 三、迁移：Trae 是第一个验证机会

把 WorkBuddy 两端收敛成客户端描述之后，接 Trae 就变成了一次**验证**——如果抽象是对的，加一个新客户端应该只写一份描述，不碰路由逻辑。

结果是成立的。`src/clients.mjs` 里多一份 Trae 的条目即可，`src/router.mjs`、`src/stream.mjs`、`src/config.mjs` 都没有为 Trae 改动。

这是这次重构最有价值的收获：**抽象是否成立，看新增一个实现时要不要改核心代码。**

## 四、现在这个结构

```
src/
├── clients.mjs         客户端描述（WorkBuddy 国内 / 国际、Trae、Qoder…）
├── router.mjs          分发——不认识任何具体产品
├── accounts.mjs        账号级状态
├── workbuddy-login.mjs 国际版专属的登录流程
├── stream.mjs          流式响应的统一处理
├── config.mjs          配置
└── manager.mjs         编排
```

各客户端之间的差异被压到两处：

1. **`clients.mjs` 的条目**——声明式描述
2. **少数专属模块**——比如国际版 WorkBuddy 的登录，流程实在无法统一

其余全部共享。

## 五、这段经历留下的两条判断

**第一，先找共性再动手改。**

最初的冲动是「让国际版也能用」，于是写了一套平行实现。真正省事的做法是先问「这两个东西除了参数还有什么不同」，答案往往比想象中少。

**第二，新增实现的成本，是检验抽象的唯一标准。**

接 Trae 时如果发现要改 `router.mjs`，说明前面的抽象没做对，应该回头改抽象，而不是在路由里加分支。这次不用改，所以认定抽象成立。

## 六、一个教训：登录流程是最难统一的部分

端点、鉴权头、参数格式这些都能描述化，唯独登录流程不行——国际版 WorkBuddy 的登录有独立的跳转与回调，Trae 又是另一套。

这部分没有强行抽象，而是留在 `workbuddy-login.mjs` 里单独维护。**该特化的地方特化，比强行统一更省事。**
